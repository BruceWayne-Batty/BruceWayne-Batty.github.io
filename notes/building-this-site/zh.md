个人网站最初看起来像一个排版问题：放上名字、项目、联系方式，再选一个不太像默认模板的字体。但当它开始承载项目和开发记录，问题就变成了另一件事：下一次更新，到底要改多少地方？

这篇记录回看的是 2026 年 10 月这轮重建，不是网站全部历史。依据是仓库提交、当前源码和构建检查；不会把设计上的取舍写成没有证据的线上故障，也不把一套测试脚本当成真实浏览器的完整验收。

## 第一阶段：先让首页说清楚「我在做什么」

10 月 21 日的 `bdb7a6f` 清理了旧站；10 月 22 日的 `ed73a81` 建立了双语 portfolio landing page。这一阶段选择的是直接的 HTML、CSS 和 JavaScript，而不是先搭一套复杂应用。

首页需要让人快速理解三件事：我是谁、我在做什么、怎样联系我。项目和笔记先作为入口出现，视觉语言则围绕深色背景、排版层级、卡片与细线组织。页面可以有性格，但不该靠动画解释内容。

这时的双语方案把两种语言放在同一份页面里，再通过浏览器脚本切换。对内容量小的单页来说，这是合理起点：布局不用维护两份，改一句文案也能立刻看到两种版本。代价是语言更像浏览器中的状态，而不是一个可以直接分享的地址。

**阶段经验：先建立清晰的信息层级，再决定系统需要多复杂。** 单页并没有做错，只是后来需要处理的内容已经不再只有一页。

## 第二阶段：视觉上能用，还不够

10 月 26 日的 `8464293` 集中完善可访问性和发布资产。这里的「问题」不是某个按钮一定已经在线上坏过，而是视觉实现与真实使用之间存在需要补齐的边界。

### 菜单藏起来了，不等于键盘访问不到

移动端菜单如果只在 CSS 中移出画面，里面的链接仍可能进入 Tab 顺序。用户看不到菜单，却能把焦点送进去，这比单纯的样式错位更难理解。

当前实现把菜单视为一套状态，而不是一个动画：

- 用 `aria-expanded` 表达开关状态；
- 在移动布局、菜单关闭时设置 `inert`；
- 打开菜单后把焦点交给第一个链接；
- 按 Escape 关闭，并把焦点还给菜单按钮；
- 处理点击菜单外部、点击链接和跨越布局断点的情况。

有些逻辑不是视觉稿里会画出的东西，但它们决定了页面是否真的可操作。

### 动画应该是增强，不是内容出现的前提

滚动显现使用 `IntersectionObserver`，同时检查 `prefers-reduced-motion`。只有浏览器支持并且用户没有要求减少动效时，才启用显现行为。否则内容保持可读，不必等一段不存在的动画。

滚动导航更新用 `requestAnimationFrame` 合并事件，监听器使用 passive；活动章节还通过 `aria-current` 表达。这类小处理，比继续增加动画更值得优先做。

### 能打开，不等于发布完整

这一阶段还加入了 404 页、favicon、分享图片、robots、sitemap 和检查脚本。分享卡片采用 1200 × 630 PNG，脚本检查文件签名和尺寸。网站不仅是浏览器里的一张页面，也会出现在搜索结果、聊天预览和失效链接之后。

## 第三阶段：项目和笔记需要自己的地址

同一天的 `2951f83` 将 Projects 和 Notes 拆成独立页面；`0fa5fe3` 又加入双语 App Store 审核记录。

这一步解决了单页的信息负担：主页不必装下所有项目详情和长文，访客可以直接进入某个主题，分享链接也不再只指向首页中的一个区域。

但独立页面越多，手工 HTML 的维护成本就越明显：导航、页脚、双语 metadata、文章卡片和列表会重复出现。一次新发布如果还要手动修改首页、Notes 列表和相关入口，就容易出现「文章有了，入口没更新」的情况。

从提交结果看，接下来的转向不是为了把技术栈做大，而是为了减少这些重复劳动。

## 第四阶段：把内容生产移到构建时

10 月 27 日的 `d6db480` 引入 Eleventy 多语言静态构建。当前开发依赖锁定 Eleventy 3.1.2 和 Cheerio 1.1.2，最终交付的仍然是 HTML、CSS、JavaScript 与图片，不需要常驻应用服务器或数据库。

### 架构：内容、模板、构建、浏览器各做一件事

```text
notes/<slug>/zh.md、en.md    src/_data/*.json
            \                /
             内容与结构化数据
                     |
          Eleventy + Nunjucks 模板
                     |
       路由 / 集合 / 校验 / HTML 语言转换
                     |
                  _site/
                     |
                GitHub Pages
                     |
     浏览器：菜单、时钟、导航、渐进动效
```

源码职责分开后，更新一篇文章不需要去动浏览器脚本：

| 位置 | 职责 |
| --- | --- |
| `notes/` | Markdown 正文及文章 metadata |
| `src/_data/` | 作者、标签、项目、站点与页面数据 |
| `src/_includes/` | 公共布局和组件 |
| `src/pages/` | 首页、Projects、Notes、归档、sitemap 与兼容页模板 |
| `eleventy.config.js` | 路由、集合、过滤器、内容校验及 HTML 转换 |
| `assets/` | CSS、浏览器脚本和图片 |
| `scripts/check_site.py` | 检查构建后的站点 |
| `_site/` | 构建产物，不是手工维护的正文来源 |

Nunjucks 负责把内容装进页面，Eleventy 负责发现内容并生成集合。Cheerio 在构建阶段处理已有双语属性，把旧页面的两套文案转换成各自语言的 HTML。这是迁移中的实用折中：保留可复用的页面结构，但不让读者再依赖客户端脚本取得正确语言。

## 双语最重要的变化：语言成为 URL 的一部分

当前路由规则很简单：中文使用根路径，英文放在 `/en/` 下。

```text
/notes/building-this-site/
/en/notes/building-this-site/
```

这样，中英文页面可以各自拥有标题、摘要、`html lang` 和自引用 canonical。`hreflang` 只指向真实存在的语言版本，而不是假定每篇文章都有翻译。

构建转换会选取相应语言的文案和 aria-label，移除另一种语言的内容区块，再清理双语属性。最终页面不是「带着两种语言等待切换」，而是已经确定语言的文档。浏览器里的脚本因此可以专注交互，而不是接管正文。

缺少翻译时，文章页明确显示暂无翻译，不把语言按钮伪装成同一篇文章的另一种版本。正文引用其他 Note 则使用 `noteLink`：优先链接同语言，缺失时链接已有语言并注明；如果整个目标不存在，就让构建失败。

旧的 `notes-*.html`、`notes.html` 和 `projects.html` 保留为 `noindex` 兼容页。新架构不应该用切断旧链接的方式宣布自己来了。

## 内容模型：把「别忘了」变成构建规则

每篇 Note 使用稳定 slug 作为身份，两种语言通过 `translationKey` 关联。改标题不改 URL，避免一次文案润色变成链接迁移。

```text
notes/
└── building-this-site/
    ├── zh.md
    └── en.md
```

Front matter 保存标题、摘要、引言、语言、作者、日期、编号、标签、草稿状态、布局和 permalink。构建器会检查必填字段、日期格式、作者和标签登记、slug 命名、文件路径和 permalink，也会核对两种翻译的作者、日期、编号与标签是否一致。

校验的意义不只是防止 YAML 写错，而是提前发现内容关系出了问题。例如，把文件放进新目录但忘了更新 slug，不应该等发布后再发现错误地址。

发布集合排除草稿，并按日期与日志编号排序。首页最新三篇、Notes 列表、标签页、作者页、上一篇和下一篇都从集合生成。添加这篇记录时，应该只需要写正文与 metadata，而不是再去维护几份文章索引。

## 发布流程：检查真正会部署的文件

本地命令与部署路径保持一致：

```bash
npm run dev
npm run build
npm test
```

`npm run build` 先清理输出再构建，避免删除或改名的文章以旧文件形式残留。`npm test` 构建站点、检查浏览器脚本语法，再运行 Python 站点检查。

检查针对 `_site`，覆盖站内文件与锚点、canonical、语言替代链接、sitemap、结构化数据、归档、首页最新三篇和分享图片，还会检查是否遗留未解析的双语属性。Notes 的 `BlogPosting` JSON-LD 由文章数据生成，而不是另抄一份标题和日期。

GitHub Actions 在推送 `main` 后安装锁定依赖、执行验证并部署 `_site`。这是静态站点的完整发布链，不需要手动把构建文件复制到发布目录。

不过，自动检查仍有边界：链接存在不代表排版好看，ARIA 属性存在不代表屏幕阅读器体验已经合格，生成了 SEO metadata 也不代表搜索引擎已经收录。浏览器、键盘、移动设备和真实分享预览仍需要人工复核。

## 问题与方案，压缩成一张表

| 问题或维护风险 | 当前处理方式 |
| --- | --- |
| 双语只是浏览器状态，不便直接分享语言版本 | 独立语言 URL，构建时生成对应正文与 metadata |
| 首页同时承担介绍、项目详情与长文 | Projects、Notes 与文章页分离 |
| 页面多了以后，公共结构和文章入口容易重复维护 | 公共模板、结构化数据与自动集合 |
| 移动菜单视觉关闭但仍可获得键盘焦点 | `inert`、焦点管理、Escape 与断点处理 |
| 动效可能成为正文显示的依赖 | 支持检测、减少动效偏好与渐进增强 |
| 标题改动或架构迁移影响旧链接 | 稳定 slug 与旧路径兼容页 |
| 无翻译或跨文引用指向不存在的目标 | 明确缺译状态、`noteLink` 回退及构建失败 |
| 删除文章后旧产物残留 | 构建前清理 `_site` |
| 只检查源码，没检查真实发布结果 | 对构建产物执行链接、SEO、数据和资产校验 |

## 现在的边界，以及下一步

这套架构适合当前需求：个人介绍、项目展示、双语长文和 GitHub Pages 发布。它不是在线编辑 CMS，也没有在这轮重建里加入账户、评论或数据库；如果未来出现这些需求，应重新评估，而不是因为「网站以后可能会变大」先把它们搭出来。

还有一些维护成本没有自动消失：翻译仍要认真核对，项目素材与事实仍要更新，视觉和辅助技术体验仍要实际测试。站点域名也出现在多处配置中，更换域名时需要同步修改，这仍有继续集中管理的空间。

这次开发最重要的结果，不是首页终于排好了，而是发布下一篇文章变得更像写作，而不是复制 HTML、补列表、检查几个地方有没有漏。

**首页负责让人认识我，Notes 负责留下过程；构建系统负责让这件事能继续做下去。**
