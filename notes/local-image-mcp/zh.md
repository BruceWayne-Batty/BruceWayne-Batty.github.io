一张图片出现在聊天窗口里，和一张图片出现在项目目录里，是两种完成状态。前者说明模型交作业了；后者才方便继续做界面、换素材，或者让下一步工具接着处理。中间那段下载、找文件、复制路径的工作，通常没有技术含量，却很擅长打断思路。

Local Image MCP 处理的就是这段接缝：让 MCP 客户端调用远端图片模型，同时把结果变成可继续使用的本地文件。这里的「Local」指服务与文件工作流，不是模型在本机推理。显卡还没有因此获得假期，也没有因此接到新任务。

这篇记录以仓库的四次提交和当前源码为依据。当前工作区还有未提交修改；下文会把它们与已提交实现分开。它不是一次发布公告，也不把源码里的能力自动换算成真实服务上的测试成绩。

## 先把桥架起来，而不是再造一个聊天窗口

项目采用 TypeScript、Node.js 20+ 和 MCP SDK，通过 stdio 与客户端通信。入口读取配置，再创建服务；工具参数由 Zod 定义，图片请求交给独立客户端，文件保存交给输出模块。整体链路是：MCP 工具调用 → 参数与配置 → 协议请求 → 图片结果 → 本地文件与返回内容。

这个分层的好处不是架构图比较整齐，而是网络接口和文件系统出了问题时，不必一起猜。MCP 层负责让工具可调用，客户端负责让服务端听懂，保存模块负责让磁盘上的东西有名字。三者都很朴素；把它们混在一起之后，朴素通常就会变成神秘。

## 「兼容图片接口」其实是两条路

OpenAI 路径使用 Images 协议：生成请求是 JSON，编辑请求是 multipart 表单。返回的图片可能是 Base64，也可能是 URL；后者还需要下载，不能只把一个链接当成本地结果。Gemini 路径则调用 generateContent，把文字和图片组织成 contents 与 parts，再从 inlineData 中取回图片数据，同时保留文字回复。

这不是把一个 GPT 模型名替换成 Gemini 模型名。编辑的上传方式、输出结构，以及比例、尺寸等参数的位置都不同。当前客户端维持统一的图片结果结构，但请求适配仍然分开；共享流程，不假装协议相同。

New API 一类服务的适配重点是可配置的 base URL 和路径拼接。源码会处理地址末尾已有 /v1 或 /v1beta 的情况，避免叠出两份版本前缀。它通过相应协议端点访问兼容网关，而不是凭「兼容」两个字保证每个上游模型都接受所有参数。网关路由和模型支持仍然需要使用者确认。

## 四次提交，几个很具体的变化

2026 年 9 月 8 日的 acd7e85 是初始提交。9 月 11 日的 983dba5（Local Implement）把本地接入继续落实：配置辅助脚本、启动说明，以及 URL 和输出处理都在这次改动里。此时的问题已经不只在 HTTP 请求上，还包括客户端究竟怎样启动服务、文件究竟保存到哪里。

10 月 21 日的 de4dde3 加入图片编辑。实际改动包括源图加载、OpenAI multipart 编辑请求和 Gemini 图文输入，也把 image\_edit 暴露为 MCP 工具。生成回答「从零做一张」，编辑则要回答「拿这张接着做」；多出来的不只是一个按钮，还有输入文件处理这整条链路。

10 月 22 日的 b60c283 只做了一件值得准确记录的小事：把配置源码和配置示例里的默认 OpenAI 图片模型，从 gpt-image-1.5 改为 gpt-image-2.5-sunburst；Gemini 默认值仍是 gemini-3.1-flash-image。提交本身没有提供质量或速度对比，也没有证明这个模型名在所有兼容服务上可用，所以这里不附赠一份性能传说。

## 从一张输入，到下一步能找到的文件

当前输入处理接受本地路径（含 ~/）、公开 HTTP(S) 地址、Base64 data URL 和裸 Base64。源图限定为 PNG、JPEG 或 WebP。不同来源先被规范化为图片字节与 MIME 类型，再交给协议适配。OpenAI 编辑把图片放进表单；Gemini 编辑把图片变成 inlineData。当前工作区还加入多图参考和批量编辑：前者把多张参考图放进同一次请求，后者逐张执行并分别记录成功或错误。它们不是同一个功能，也不是自动并行。

输出同样需要收口。结果被保存到配置目录；未配置时，output 会相对服务进程的工作目录解析。工具同时返回图片内容、可读说明和包含文件路径的结构化结果。对于接下来的本地工具，稳定的文件路径比从聊天里重新取图更实用；启动服务时的工作目录，也因此不再是一个可以随便忽略的细节。

当前工作区的保存实现还处理扩展名与图片类型、文件名前缀清理、重名避让，并用独占创建避免悄悄覆盖旧文件。这些细节不提高审美，但能避免第二张图把第一张图变成回忆。

## 工作区里的下一层：少传一次上下文

未提交代码把工作流往前推了一步：generate\_image 和 image\_edit 之外，增加 batch\_image\_edit、multi\_image\_reference、image\_edit\_continue、image\_edit\_history 和 server\_info。会话记录持久化到输出目录下的 .image-mcp-sessions，可以继续编辑、查看历史，或指定父版本分支。它靠父版本图片、提示词上下文与约束延续工作，不是上游模型的原生聊天会话。

这里有一个比工具数量更有意思的取舍：API 请求成功、图片保存成功之后，才提交会话的新版本；失败不推进版本。批量编辑则逐项请求、逐项保存，允许部分成功。前者避免历史里出现不存在的图，后者避免最后一项失败时前面的成果一起陪葬。保存模块本身也会在单次多图写入失败时清理该次已写入的文件。

除了已有的负面提示，这批改动还暴露背景、输出格式、压缩和输入保真度等选项，并对协议相关参数做限制。例如 mask 和 inputFidelity 走 OpenAI 编辑路径，负面提示则拼进文字提示。能把参数发出去，不等于所有兼容网关都会照办；这里仍然有模型和服务端的边界。

这些能力已经出现在当前源码中，但没有包含在上述四次提交里。把「工作区里写了」和「发布版本里有了」分开，是开发记录最便宜也最有效的降噪方式。

## 默认值是起点，不是猜测模型的替代品

配置优先使用环境变量，其次读取本地 JSON，再采用字段默认值；NEW\_API\_BASE\_URL 和 NEW\_API\_KEY 都是必需项。没有显式配置时，协议默认是 OpenAI，模型是 gpt-image-2.5-sunburst；Gemini 路径的默认模型是 gemini-3.1-flash-image。模型名仍需与网关实际路由对应，调用参数也允许覆盖模型。请求超时默认 120 秒，配置文件位置可由 IMAGE\_MCP\_CONFIG 指定，输出目录由 IMAGE\_OUTPUT\_DIR 控制。

配置读取会检查协议、Key 和超时。请求层报告 HTTP 状态及截断后的服务端错误内容，超时给出明确错误；MCP 层把异常转换为带 isError 的工具结果。空的图片结果也不会被当作成功保存。错误处理的目标是让失败可定位，而不是让每一次失败都说「出了点问题」。这句话很礼貌，但几乎没有职业技能。

## 本地工具并不天然安全

API Key 通过配置或环境变量提供，不属于工具调用参数。环境变量可以避免把 Key 直接写进项目文件，但本地 JSON 配置仍然是明文凭据，不能提交或公开。图片本身会发送给远端服务；「本地 MCP」不意味着素材不会离开电脑。本地路径的可读范围也由运行进程的权限决定，并没有因此获得项目目录沙箱。

当前工作区的下载模块检查 HTTP(S) URL、拒绝带凭据的地址与私有网络目标，对重定向逐跳检查，并限制下载大小为 20 MiB、验证图片签名。源码也明确提醒：DNS 检查不是地址绑定，抵抗 DNS rebinding 还需要出站网络策略或固定已验证地址的传输层。这是防线，不是「SSRF 已彻底解决」的奖状。

文件写入有重名保护，但仍然应限制运行权限与输出位置。远端错误内容目前会进入错误信息，也不应未经检查就贴到公开日志。安全处理和好用不是二选一；只是安全通常没有一张漂亮的效果图。

## 边界，以及还可以往哪里走

现在的定位是本地 MCP 桥接器，不是离线生成器、完整图片编辑器或托管服务。兼容层也不保证模型有同样的能力；本地会话记录也不等于完整的素材管理或备份系统。仓库中有请求与文件保存等测试代码，但这篇记录没有运行源项目测试，也没有验证真实 Gemini、OpenAI 或 New API 服务，不能据此声称端到端通过。

接下来可以做的，是为具体网关建立可重复的兼容性测试，补上更清楚的参数能力说明，收紧输入路径权限，并改善凭据与错误信息的管理。会话记录的迁移与清理、资源限额和下载传输层加固也值得考虑。这些是改进方向，不是把未来功能偷偷写成现在时。

> 这类工具的价值，不一定是多生成一张图。也可以是少让人找一次下载目录。

把模型接上只是第一步。真正的开发记录，往往写在那些不太值得截图的地方：地址少一个重复前缀，失败多一句有用解释，磁盘上留下一张下一步确实找得到的图。
